## 2. `rank-the-shelf.ts` — internal organisation

Run:

```
PATH="$HOME/.nvm/versions/node/v24.18.1/bin:$PATH" node docs/active/work/T-013-03/rank-the-shelf.ts
```

Node 24 strips the types natively, so `src/lib/*.ts` imports work with no build step. Imports, and
nothing else from the repo:

```ts
import { buildSchedule, handsOnEvidence } from '../../../../src/lib/schedule.ts';
import { costOf, servingsOf }              from '../../../../src/lib/scaling.ts';
import { diagnose }                        from '../../../../src/lib/meal.ts';
```

`src/generated/recipes.json` is read with `readFileSync`, as T-012-02's script does. `slack`,
`keeps`, `washingUp` and `capacity` arrive already parsed, so the readers in `src/lib/slack.ts`,
`keeps.ts` and `washing-up.ts` are **not** imported — importing them to re-parse an object would be
a second reading of the same line.

### 2.1 Section order in the file

```
  header comment          why this file exists, how to run it, and the no-tuning rule
  §A  PROFILES            the two profiles as DECLARED TABLES — the reviewable surface
  §B  reading             one pass over 685 files → a Row per recipe
  §C  scoring             Row → Verdict {ranked | rejected | cannot-say} + score
  §D  the two lists       sort, rank, print top/bottom
  §E  overlap             the four metrics from design.md §3
  §F  inversion           the three tests from design.md §4
  §G  coverage            how many clear each profile, how many are separated, what is assumed
  §H  the seventeen       T-013-01 §3.5's table, reproduced or contradicted
  §I  the meal            slot rules, then diagnose() at cooks 1 and 2, printed raw
```

### 2.2 §A — the profiles as data

The one structural rule inherited from T-012-02: **a decision a reader might disagree with is a
line in a table, not a branch inside a function.**

```ts
interface Profile {
  name: string;
  /** Higher is better. The family profile sets this false; §3.3's score is a cost. */
  higherIsBetter: boolean;
  /** Every weight, in minutes-equivalent, signed as the occasion signs it. */
  rates: {
    standingPerMinute: number;
    longestPerMinute: number;
    washingUpPerThing: number;
    keepsPerDay: number;
    keepsCapDays: number;
    slackForgiving: number;
    slackUnforgiving: number;
  };
  /** True on the party: §3.6's rule. Both clauses travel together because they are one rule. */
  claimedMinutesOnly: boolean;
  /** occasions.md's section, so every number is traceable to a line of prose. */
  source: string;
}
```

Two entries, `FAMILY` and `PARTY`, transcribed from `occasions.md` §3.3 and §3.4. The gate is not a
rate and lives in §C as a named function per profile, because it returns a *verdict* rather than a
number.

### 2.3 §B — `Row`, one per recipe

```ts
interface Row {
  slug: string;
  category: string;
  writtenServings: number | null;
  /** Null when costOf() returned null. */
  standingAt: number | null;
  assumedStandingAt: number;
  longestAt: number | null;
  washingUpCount: number | null;   // null = never declared; 0 = declared as nothing
  keepsDays: number | null;        // null = never declared; 0 = "not at all"
  slackLevel: 'forgiving' | 'narrow' | 'unforgiving' | null;
  evidence: 'stated' | 'inferred' | 'unknown';
  bindsAt12: boolean;
  untimedCount: number;
}
```

`washingUpCount` and `keepsDays` are **nullable and the null is load-bearing**. A recipe that
declared `>> washing-up: nothing` and a recipe that never mentioned the sink both contribute zero
to the score, and the difference between them is the whole subject of §G's third diagnostic. The
type keeps them apart even where the arithmetic cannot.

### 2.4 §C — one `Verdict` type, both profiles

```ts
type Answer = 'ranked' | 'rejected' | 'cannot-say';

interface Verdict {
  answer: Answer;
  /** Null unless ranked. */
  score: number | null;
  /** Always set: the gate clause or the rule that decided it, in words. */
  because: string;
}
```

`because` is a **required** field even on `ranked`, so every one of 1,370 verdicts (685 × 2) can be
explained without re-reading the code. It is the mechanism that makes "cannot say" a real third
answer rather than an empty bucket: `no readable servings`, `evidence: unknown`,
`slack: unforgiving`, `scored`.

Scoring is one function taking `(row, profile)`; the sign flip is entirely in `profile.rates` and
`profile.higherIsBetter`. **There is no `if (occasion === 'party')` anywhere in the arithmetic** —
that is `occasions.md` §3.2's claim ("the same number, one sign") asserted structurally rather than
described.

### 2.5 §D–§H — the reported numbers

Ranking: sort ranked rows by score (ascending for FAMILY, descending for PARTY), ties broken by
slug so the output is deterministic and re-runnable. **Rank numbers are competition-ranked** —
equal scores share a rank — because a tie printed as 4th and 5th invents a distinction the profile
did not make, and §G's whole point is how many ties there are.

Printed per profile: top 20, bottom 20, the three counts (ranked · rejected · cannot-say, split by
cause), distinct-score count, largest tie group.

Overlap: `top10Intersection`, `jaccardOverRanked`, `spearman` over the intersection of the two
ranked sets, and the seventeen-row reproduction of §3.5.

### 2.6 §I — the meal

Slot rules, declared as a table before the ranking is consulted:

| Slot | Rule |
| --- | --- |
| centrepiece | the best-ranked file that is a whole roast or braised main |
| starch | the best-ranked potato/bread/grain side |
| vegetable | the best-ranked non-starch vegetable side |
| sauce | the best-ranked sauce or gravy |
| make-ahead | the best-ranked file declaring `keeps ≥ 1 day` that is not already chosen |

The slot **assignment** is by hand from the printed ranking and pasted into the script as a slug
list, with a comment naming the rank each came in at, rather than machine-classified: five hand
choices with their ranks written down are more reviewable than a sixth vocabulary table, and
T-012-02's script already demonstrates how much vocabulary table one document can carry before it
stops being readable.

`diagnose()` is then called twice — `{cooks: 1}` and `{cooks: 2}`, `burners: 4`,
`ovenShelves: null` — and both `Diagnosis` objects printed as formatted JSON.

## 3. `docs/gaps/two-that-invert.md` — outline

Mirrors `what-the-shelf-offers.md`'s shape: what this reading is, how it was run, the numbers,
then a ranked recommendation. **No `## What it has` heading anywhere in the file**, per
`design.md` §7.

```
  # Two occasions, run against the whole shelf
      what this is · the date and the file count · the command · what it builds (nothing)

  ## 1. Are they real — somebody sells for it
      1.1 The holiday meal — four kinds of evidence, linked, one line each on what it established
      1.2 The dumpling party — the harder case, pushed
      1.3 What is actually sold, and why it matters to the profile

  ## 2. The two rankings
      2.1 How the profiles were transcribed (and that no rate was changed)
      2.2 The holiday list — top ten, read as a cook, verdict
      2.3 The dumpling party list — top ten, read as a cook, verdict
      2.4 The three answers, per profile, by cause

  ## 3. Do the lists differ — the overlap number
      the headline number, the three supporting ones, and what a high number would have meant

  ## 4. The inversion test
      three ways, all three results, stated either way

  ## 5. Can the shelf feed either
      per occasion: how many clear · how many are good · what is missing
      cross-referenced against what-the-shelf-offers.md §4's "write food before writing features"

  ## 6. The holiday meal, diagnosed
      the plate and the slot rules · the pasted Finding[] · the sentence it produces
      · does it explain a real afternoon

  ## 7. Recommendation
      per occasion: open · open after writing food · do not open — argued, with what it would take
```

Sources are linked inline **and** grouped at the end by what each established, which is
`soup-pot.md`'s "Where this came from" shape and the one the ticket names.

## 4. Ordering, and why it matters

The order is not arbitrary — three of these steps can invalidate the ones after them.

1. **Regenerate `src/generated/recipes.json`.** Every count below is against it. *(done — 685
   files, md5 `f83cf3586331856f919bb747b3c0476a`)*
2. **Capture `node scripts/menu-sections.mjs` output** *before* `docs/gaps/two-that-invert.md`
   exists. Without the before, the after proves nothing.
3. **Write §A–§C of the script and reproduce `chili-con-carne` = −95.0.** If the transcription does
   not reproduce `occasions.md`'s own worked number, everything downstream is measuring a different
   profile. **This is a stop-the-line check.**
4. **Run the full ranking.** Every number in §2–§5 of the document.
5. **Gather the selling evidence.** Independent of 3–4, and can be done in parallel, but it lands
   in the document before the rankings because a ranking for an occasion that is not real is not a
   finding about anything.
6. **Assemble the meal and run `diagnose()`.** Depends on 4 — the plate is chosen from the ranking.
7. **Write the document.**
8. **Re-run `menu-sections.mjs` and diff against step 2.** Byte-identical, or the file is wrong.
9. **`npm run verify`.** Nothing here should move it, and that is the claim being checked.

## 5. Interfaces this ticket does not touch

Stated so a reviewer can confirm the blast radius is zero:

- **No new export anywhere in `src/lib/`.** The script consumes `buildSchedule`, `handsOnEvidence`,
  `costOf`, `servingsOf` and `diagnose` at their current signatures.
- **No new field on any `.cook` file**, and no `>> occasion:` line proposed, written or reserved.
- **No entry in `src/data/counters.json`**, no route, no page, no component.
- **No test file.** The script's stop-the-line check (step 3 above) is an assertion inside the
  script that exits non-zero on failure, which is where it belongs: it guards *this reading*, and a
  `vitest` file guarding a work-directory script would be a permanent test of a one-off document.
