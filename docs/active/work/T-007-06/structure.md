## 3. `src/lib/counters.ts`

One function changes; the module's public surface is unchanged.

**Unchanged exports:** `Counter`, `counters`, `counterBySlug`, `counterByName`, `principalIngredients`,
`MenuSection`, `Menu`, `menuFor`, `menus`. No new export — a validator exported for a caller that
may not be edited is a validator nobody calls (design §B).

**`menuFor` — the sectioned branch only.** Today:

```ts
items: items.map((slug) => bySlug.get(slug)).filter(Boolean) as RawRecipe[],
```

becomes a resolve-and-collect: build `{ title, items }` while pushing every unresolved
`{ title, slug }` onto a `missing` array shared across sections. After the map, if `missing` is
non-empty, throw a single `Error` naming all of them at once — one build failure listing nine
slugs beats nine successive failures.

Message shape (one block per offending section, so a reader sees the heading the slug was listed
under):

```
Cha Chaan Teng lists 5 recipes that do not name this counter:
  "Toast and the bun case" — pineapple-bun (shelved at Bakery, Dim Sum Counter)
  "Toast and the bun case" — egg-custard-tart (shelved at Dim Sum Counter, Bakery)
  ...
A section orders what a shelf already holds; it cannot put a recipe on one.
Either add "Cha Chaan Teng" to that file's >> counters: line, or drop the slug from
src/data/counters.json. docs/knowledge/counters.md#sections says why.
```

A slug that names no recipe at all reads `(no recipe with that slug)` instead of the shelved-at
list. Resolving that needs `all`, not `mine` — the lookup for the *diagnostic* is over `all`; the
lookup for *membership* stays over `mine`. Keeping those two separate is the whole point of the
change and should be said in the code comment.

**Everything after the throw is untouched:** empty-section filtering, the `Also` sweep,
`count: mine.length`, the category-fallback branch, `menus()`.

**Doc comment.** The block comment above `menuFor` gains the rule in one sentence — that a section
orders the shelf and cannot extend it — so the file states the contract the docs now describe.

## 4. `src/lib/counters.test.ts` (new)

Vitest, matching the sibling `src/lib/*.test.ts` style. Builds small `RawRecipe`-shaped fixtures
rather than importing the generated collection, so the test states the rule rather than the data.

| Test | Asserts |
| --- | --- |
| sections print in the counter's order | not alphabetical, not by size |
| a listed slug not naming the counter throws | error message contains the counter name, the section title and the slug |
| the throw names *where the recipe actually is* | message contains the other counter's name |
| a listed slug matching no recipe throws | message says no recipe has that slug |
| a shelved recipe no section lists lands in `Also` | `Also` is still legitimate, and last |
| a section that empties is dropped | only when it was empty in the data, not by dropping items |
| `count` equals the recipes naming the counter | and equals the number of items rendered |
| no-sections counter falls back to category grouping, biggest first | unchanged path still covered |

Fixture note: `RawRecipe` is wide (27 fields). Use a small `recipe(slug, counters, extras?)` helper
returning a minimal object cast to `RawRecipe`, as the sibling tests do for their own shapes.

## 5. `scripts/check-menus.mjs` (new)

Post-build checker. Reads only files; writes nothing; safe to run concurrently.

```
node scripts/check-menus.mjs          # after astro build
```

**Inputs:** `src/data/counters.json`, `dist/menu/<counter.slug>/index.html`.

**Parse.** Split the built page at `<h2>` boundaries inside `.menu`, giving an ordered
`[{ heading, slugs }]` from `data-slug="…"` attributes; read the stated count out of
`<p class="count">N recipes</p>`. Regex-level parsing, matching `check-overflow.mjs`'s existing
approach to `dist/` — no HTML dependency is added.

**Three assertions per counter** (design §C): listed-and-printed; printed-under-its-own-heading;
stated count equals printed count. A counter that renders no page is a failure *only* if it has
listed slugs — `menus()` legitimately omits a counter with nothing on it.

**Output.** One line per counter, all 22, even when clean — the ticket asks for the output over all
twenty-two, and a checker that prints only failures cannot show coverage:

```
  ok   Bakery                      5 sections, 107 listed, 107 printed, count 107
  ok   Cha Chaan Teng              5 sections,  27 listed,  27 printed, count 27
  FAIL One Pot                     5 sections,  77 listed,  73 printed, count 73
         listed but not printed: general-tsos-chicken, orange-chicken, …
```

then a total line and `process.exit(1)` on any failure. Missing `dist/` exits 1 with "run
`astro build` first", so a bare invocation cannot pass vacuously.

## 7. `docs/knowledge/counters.md`

Insert a short `### Sections` block immediately after the existing two-line fallback paragraph
(lines 21-22), before the `---` and the Contents table — that paragraph is already the file's only
statement about `counters.json`, so the section rule belongs beside it. Roughly fifteen lines:

- what `sections` is: the headings a counter's menu prints, in print order, derived from the gap
  notes by `scripts/menu-sections.mjs`;
- **the rule**: a section orders what the shelf already holds; membership is the `>> counters:`
  line and nothing else;
- what happens when they disagree: `menuFor` throws with the slug named, `astro build` fails,
  `node scripts/check-menus.mjs` reports it over all counters after a build;
- how to list a dish on a second shelf: add the counter to that recipe's `>> counters:` line —
  one line in one file;
- the history, in one sentence, because the doc being silent is half of this bug: nine listed
  slugs vanished off two pages for two stories and the pages looked right the whole time.

Voice: the file's own — plain, declarative, no jargon. No table; this is a rule, not a vocabulary.
