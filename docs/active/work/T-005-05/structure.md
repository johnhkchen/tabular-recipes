## 2. Attempt-private tooling

Lives in `.lisa/attempts/T-005-05/1/work/`. None of it is repository source; it is published with
the artifacts so the judgement is reviewable without opening 183 files.

```
dump-rows.mjs      already written — stats · tsv · over · source · slugs · cols
dump-work.mjs      already written — the reading list: every over-cap row with its slack line
slack-echo.mjs     new — content-word overlap between each row and its file's slack reason
apply-rows.mjs     new — validates rows-after.tsv against the tree, then writes
rows-before.tsv    generated — all 393 rows as they stand
rows-after.tsv     hand-authored — the deliverable
cols-before.txt    generated — the whole merge tree, one line per recipe
cols-after.txt     generated — must diff empty against cols-before

report-after.txt   generated — npm run check, prose row 0
```

### `rows-after.tsv` — the shape

Tab-separated, one line per over-cap row, no header line.

| Column | Meaning |
| --- | --- |
| 1 `path` | repository-relative `.cook` path |
| 2 `kind` | `header` / `footer` — informational, the applier does not trust it |
| 3 `step` | 1-based step number, the same N as `>> step.N:` |
| 4 `source` | `step.N` / `paragraph` — which edit site |
| 5 `was` | the rendered text today, in full. **The match key.** |
| 6 `now` | the rewritten row, as it will be written into the file |
| 7 `moved` | `-`, or `counter :: section` where a sentence went |
| 8 `dropped` | `-`, or a short tag: `shelf`, `justify`, `provenance`, `meta`, `echo-slack` |

Columns 7 and 8 are the accounting the acceptance criteria ask for — *every sentence removed is
accounted for* — and they are data rather than prose so the counts can be totalled rather than
claimed.

### `apply-rows.mjs` — the interface and the guards

```
node .lisa/attempts/T-005-05/1/work/apply-rows.mjs --check           # validate only, write nothing
node .lisa/attempts/T-005-05/1/work/apply-rows.mjs --apply <prefix>  # write, restricted to a path prefix
```

Two passes. **Nothing is written until every row in the table has passed every guard.**

Validation, per row:

1. `path` starts with `recipes/` and the file exists.
2. The file parses through `normalise()` and builds a tree.
3. Step `N−1` exists, has zero ingredients and zero refs — *it is a prose row*.
4. The row's current rendered text equals column 5 exactly. A stale table cannot overwrite a
   target that has moved.
5. Column 4 agrees with the file: `step.N` ⟺ the step has a `labelOverride`.
6. `now` contains no `@`, `#`, `~`, `{`, `}` — a prose row cannot acquire an ingredient, a piece
   of cookware or a timer, because any of those moves the tree.
7. `now` is non-empty and its **rendered** length (post-`cleanLabel` for a paragraph, verbatim
   for a `step.N` line) is 1–120.
8. No duplicate `path`+`step`.

Post-write, per file, before the next file is touched:

9. The file still parses.
10. `steps.length` is unchanged.
11. The set of `step.N` metadata keys is unchanged, and every value except the one being written
    is byte-identical.
12. Every other step's `rawLabel`, `ingredients`, `refs` and `timers` are byte-identical.
13. The rebuilt tree's `root.col`, `leaves.length`, `headers.length`, `footers.length` and every
    operation's `col:row:rowSpan` are unchanged.

Guard 13 is design §7's proof applied per file at write time, so a mistake is caught on the file
that caused it rather than 40 files later.

On any failure the file is restored from the in-memory original and the run exits non-zero.

### `slack-echo.mjs`

Reads `src/generated/recipes.json`. For each recipe with both a `>> slack:` reason and a prose
row, stems the content words of each (stopwords removed, plural/`-ing`/`-ed` trimmed), and prints
every pair sharing ≥3 content stems, worst first, with both texts in full. Output to
`slack-echo.txt`. Judged by hand; the tool only decides what gets read.

## 3. `src/data/counters.json` — the shape of an addition

The field exists and is validated. This ticket only adds entries.

```json
{
  "title": "Braises, left alone all day",
  "items": [ "…", "baked-turkey-wings-slow-cooker", "…" ],
  "notes": [
    { "note": "a sentence about the section" },
    { "of": "baked-turkey-wings-slow-cooker", "note": "a sentence about that dish" }
  ]
}
```

Constraints already enforced by `scripts/parse-recipes.mjs`, so a mistake fails `npm run recipes`
rather than reaching a page:

- `notes` is a list; each entry has non-empty `note`; `note` ≤ 120 characters.
- `of`, when present, is a slug **listed in this section's `items`**.
- that slug's recipe must actually be shelved at this counter, or neither it nor its note renders.

`src/lib/counters.ts` still types a section as `{ title, items }`. **This ticket does not change
it** — it is not in the ticket's file list, and T-005-03 already recorded the gap as a
recommendation with `[counter].astro`'s local cast as the current answer. Restated in the review
so it does not get lost a second time.

## 4. Ordering

The order is forced by one thing: `npm run check` and `dump-rows.mjs` both read
`src/generated/recipes.json`, which `npm run recipes` regenerates from the `.cook` files. So every
measurement is *regenerate, then measure*.

```
0.  cols-before.txt, rows-before.tsv, report-before.txt        the baseline
1.  slack-echo.txt                                              what to read against the slack line
2.  read work-list.txt shelf by shelf → rows-after.tsv          the judgement, ~232 rows
3.  apply-rows.mjs --check                                      no file written yet
4.  apply-rows.mjs --apply recipes/stews-and-braises            70 rows
    npm run recipes && npm run check                            prose row 232 → 162
    lisa commit-ticket
5.  … same for soups (47), rice-beans-and-grains (26), then the tail, one commit per group
6.  counters.json: every moved sentence, one edit
    npm run recipes                                             the validator runs here
    lisa commit-ticket
7.  cols-after.txt; diff against cols-before.txt → empty
8.  npm run verify                                              658 draw a table, 833 tests, build
9.  npm run verify:mobile                                       against a frozen dist
```

Step 6 lands after the `.cook` edits, not before, because a note may only name a slug the section
already lists — and reading the row is what decides which counter the sentence is true at.

## 6. What could go wrong, and where it is caught

| Risk | Caught by |
| --- | --- |
| a rewritten paragraph picks up an `@ingredient{}` and becomes an operation | guard 6, then guard 13 |
| a rewritten row is deleted entirely and the table renders an empty band | guard 7 (non-empty) |
| a `step.N` line is renumbered or dropped | guard 11 |
| a comma-joined rewrite renders as a run-on | design §4's rule, and the rendered text in `rows-after.tsv` column 6 is what guard 7 measures — so the TSV shows what the page shows |
| an edit lands in the wrong file's paragraph | guard 4, the exact-match key |
| a note names a slug its section does not shelve | `parse-recipes.mjs`, at `npm run recipes` |
| a sentence is moved twice | the four in `T-005-03/progress.md` §Step 8 are struck from the source rows, and `rows-after.tsv` column 7 is the whole record of what moved |
| T-005-06 later edits a paragraph this ticket rewrote | it cannot: T-005-06's boundary is bodies under a `step.N` line, and a paragraph-sourced row has none |
