## A. `docs/knowledge/voice.md` — new

A page, not a manual. Target ~110 lines. Section order is fixed because the first section is
the one everything else derives from.

```
# Voice
  (one-paragraph frame: who this is for and when to read it)

## Who is reading, and what they are holding
  The load-bearing distinction, stated once and short:
    a sentence about the dish is for them; a sentence about how the site works out
    its numbers is not.
  Second rule, from the story: shelf talk belongs on the counter's menu.

## Where the words go
  Table of the five prose fields:
    | Field | Where it lands | What it is for | What does not go here |
  Five rows: >> step.N:, step body prose, a step with no ingredients,
             >> slack:, ingredient (note).
  Prose note under the table for the two non-obvious mechanics:
    - a step with no ingredients renders three times (table, prep, cook)
    - a >> step.N: line discards the step's own prose entirely

## One fact, three lengths
  The tonkotsu worked example. recipes/soups/tonkotsu-broth-instant-pot.cook quoted
  at all three lengths (slack 241, step.1 128, opening paragraph 447), then the
  one-line diagnosis and the fix.

## The house tests
  1. Would a friend say this at a kitchen table?
  2. Does it change how you cook it?
  3. Say it once.

## The caps
  Table: field | cap | what the number is for.
  One line pointing at scripts/check-recipes.mjs as the source of truth, and one
  line saying the checker reports today and will fail later.
```

Constraints on the copy itself, from the user-global brand voice: plain kitchen-table English,
no jargon a friend would not say at a table. That rules out "inference", "derived", "surface",
"field-level constraint" in anything quoted as example copy — though the document may name the
fields, because a writer editing a `.cook` file is holding the file.

**Boundary:** `voice.md` states the aim; `check-recipes.mjs` holds the number. The caps table
in `voice.md` repeats the numbers for readability and says which file wins. When a cap changes,
the script changes and this table follows.

## B. `scripts/check-recipes.mjs` — modified

107 lines today. Roughly +55, no restructuring of what is there. The file's existing shape is
kept: header comment, imports, constants, argument parsing, one loop over targets, one summary
line, one `process.exit`.

### B1. Header comment (lines 1–9)

Extended by two sentences: the checker now also measures how much a recipe says, and that half
reports without failing. The existing promise — *"Writes nothing, so any number of these can
run at once"* — still holds and stays.

### B2. New import

```js
import { cleanLabel } from '../src/lib/label.ts';
```

Needed for the discarded-body measure: the body's rendered length is `cleanLabel(rawLabel)`,
the same function `tree.ts` uses for a step with no override. Importing it rather than
re-implementing keeps one definition of "what this step would have read as".

### B3. New constants, after `KNOWN_COUNTERS` (~line 27)

```js
// Per-field caps ... one comment line per number naming the measurement it came from.
const CAPS = {
  'operation cell': 70,
  'step body':      150,
  'prose row':      120,
  'slack reason':   200,
  'ingredient note': 80,
};

// T-005-07 flips this to true. ONE LINE.
const CAPS_FAIL_BUILD = false;
```

The keys are the field names as printed, so the report and the constant cannot drift apart.

Each cap carries a one-line comment with its justification, because the number is the whole
argument and a reader of the script should not have to find `design.md`:

```js
  // 3077 cells, mean 24, max 70. Healthy and left alone — this is a ratchet, not a cut.
  'operation cell': 70,
  // The median body stops being one sentence between 125 and 150.
  'step body': 150,
  // The trough between prep lines (<=74) and essays (>=125). Renders 3x, so 360 chars paid.
  'prose row': 120,
  // No trough: 65% of reasons sit at 225-299. 200 is the last point below the plateau.
  'slack reason': 200,
  // p99 is 63. Past 80 it is a paragraph in a table cell.
  'ingredient note': 80,
```

### B4. Findings accumulator

```js
const overCap = [];   // { rel, field, length, cap, where, excerpt }
```

Declared beside `let failed = 0` (line 39). One array for the whole run; ranking needs the
collection.

### B5. Measurement inside the existing loop

The loop body today reads:

```js
const recipe = normalise(source, {...});
...
const grid = layout(buildTree(recipe));
```

Split into two so the tree is addressable, because `tree.headers` and `tree.footers` are the
prose rows:

```js
const tree = buildTree(recipe);
const grid = layout(tree);
```

Then one call, placed **after** `findTilingErrors` and **before** the `if (!problems.length)`
branch, so a file that draws a table and a file that does not are both measured:

```js
overCap.push(...measure(rel, recipe, tree));
```

### B6. `measure(rel, recipe, tree)` — new module-scope function

Placed above the loop, beside the other top-level helpers. Pure: takes the parsed recipe and
its tree, returns an array of findings, writes nothing.

Walks five sources, one per field:

| Field | Source | Locator printed |
| --- | --- | --- |
| `operation cell` | `recipe.steps` where `ingredients.length \|\| refs.length`, text `labelOverride ?? cleanLabel(rawLabel)` | `step N` |
| `step body` | the same steps, but only where `labelOverride` is set; text `cleanLabel(rawLabel)` | `step N` |
| `prose row` | `tree.headers` and `tree.footers` | `row above the table` / `row below the table` |
| `slack reason` | `recipe.slack?.reason` | `slack:` |
| `ingredient note` | `step.ingredients[].note` | `step N, "<ingredient name>"` |

The op/prose split is read from the tree rather than re-derived, so the checker cannot disagree
with what the page will draw. `recipe.steps` is used for the two step-level fields because the
tree does not carry `rawLabel`; the `isOpStep` predicate is re-stated once, in one place, with
a comment pointing at `src/lib/tree.ts` as its origin.

Excerpt: first ~60 characters of the offending text, so a downstream ticket can recognise the
line without opening the file.

### B7. The report block

Printed after the per-file loop and after the existing `all N file(s) draw a table.` summary,
so the current output is unchanged when nothing is over cap. Emitted only when `overCap` is
non-empty.

```
────────────────────────────────────────────────────────────────
23 field(s) over cap in 12 file(s) — 4,812 characters over.

  +610  prose row       730/120  recipes/rice-beans-and-grains/boston-baked-beans-slow-cooker.cook
        row above the table  "A bean pot and a slow cooker are not the same machine…"
  ...

by field:  prose row 232 · slack reason 304 · step body 551 · ingredient note 17 · operation cell 0

Caps are reported, not enforced: this run exits 0.
Set CAPS_FAIL_BUILD = true (scripts/check-recipes.mjs) once the collection is clean.
```

Ranking key is **overage** (`length - cap`), worst first, so the field with the biggest cut
sorts to the top regardless of which cap it is measured against. Ties break on path then field,
so the output is stable run to run — a downstream ticket can diff two reports.

The total line carries three counts the ticket asks for: findings, files, and characters over.
The per-field tally is the extra that makes the report usable as a work list for three
different tickets.

### B8. The exit

Today:

```js
process.exit(failed ? 1 : 0);
```

Becomes:

```js
process.exit(failed || (CAPS_FAIL_BUILD && overCap.length) ? 1 : 0);
```

Structural failures keep failing, exactly as before. Cap findings are inert until
`CAPS_FAIL_BUILD` is `true`.

**T-005-07's change is the `false` in the `CAPS_FAIL_BUILD` declaration (§B3).** One token, one
line, no other edit. `plan.md` and `review.md` name the line number after the file is written.

## Ordering

1. `voice.md` first. The document is what the caps enforce; writing it first means the numbers
   get a reason stated in prose before they get a reason stated in a comment.
2. `check-recipes.mjs` second.
3. Report generated last, into the work directory, from the finished checker.

The two source files are independent — neither imports the other — so the order is about
thinking, not about breakage.

## Public interfaces

Nothing new is exported. `measure()` is module-scope and unexported; `check-recipes.mjs` is a
script, not a module, and has no importers (`grep` for it finds only `package.json`'s `check`
script). No test file imports it, so no test contract changes.
